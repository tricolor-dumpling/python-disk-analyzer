## 🔴 高优先级问题（2 个）

### 1. 对比报告的「合计」存在层级重复计数

**位置**：`compare.py` L147-155（`compare_snapshots`）、L186-196（`diff_from_current`）

`total_baseline / total_current / delta_total` 直接把所有目录行求和，但扫描本身是自底向上聚合的（父目录大小已包含子目录），同一个字节被计入多次。

**实测复现**（测试夹具）：

- 基线：root=7050B（含 b=6000、c=4000、a=1000）
- 变更后真实总量：7050 → 6050 = **真实变化 -1000 B**
- 报告实际输出：

```
-6000.00 B  合计变化 | 基线 17.63 KB → 当前 11.77 KB（共 4 条差异）
```

其中 17.63 KB = 7050+6000+4000+1000（root/b/c/a 四行相加），严重虚高且自相矛盾。行级 delta 正确，底部合计失真。CLI `--baseline` 与 Web `/api/compare` 均受影响（前端「基线总大小/当前总大小/总变化量」三张统计卡同样展示错误数值）。

### 2. 快照日配额是「文档功能」，实际从未执行

**位置**：`snapshots.py` L368-379（定义）、L500-572（save_snapshot 未调用）

README 声称「写盘前检查当日全局写量（默认 102.4 MiB/天）」，但 `day_write_budget_ok` / `record_day_writes` 只出现在三处：定义处、`main.py` 兼容层 re-export、单元测试 —— **`save_snapshot` 保存链路一次都没有调用它们**。快照落盘实际没有任何日写量上限，属于「文档有、实现无」的功能缺口。

## 🟡 中优先级问题（4 个）

### 3. Everything SDK 并发调用缺少互斥（注释承诺与现实不符）

**位置**：`app.py` L65-82（/api/health）、`tui.py` `_start_deep_refresh`、`cli.py` `_auto_save_on_exit`

- `app.py` 头注释称「所有与 Everything SDK 的接触都共用 GLOBAL_SCAN_LOCK」，但 `/api/health` 的 `is_everything_ipc_ready` **不持锁**直接发起 SDK 查询，与后台全量扫描并发时会踩踏 DLL 内部全局查询状态（Everything SDK 的 `SetSearchW/QueryW` 状态非线程安全，同一 DLL 模块内全局共享）；
- TUI 按 `R` 深扫在后台 daemon 线程执行，同样不持有任何锁；此时按 `Q` 退出 → `cli._auto_save_on_exit` → `compute_fingerprint` 会与深扫线程**同进程并发调用同一 DLL 实例**，查询互相污染的风险真实存在；
- `dispatcher.py`（统一调度器，进程内并发=1 + 防抖 + 代际令牌）正是为解决该问题而设计，但生产路径（scan/tui/app/fullscan）**没有任何地方使用它**——纯死代码。

### 4. TUI 深刷后光标索引可能越界崩溃

**位置**：`tui.py` `_apply_scan_result()`（约 L434-441）、主循环 Enter/↑ 分支

深刷结果替换 sizes/contents 后不收敛 `selected_idx`：深刷前在某大目录选中第 80 项 → 深刷后该目录只剩 10 项 → 按 `↑` 或 `Enter` 时 `items[selected_idx]` 直接 `IndexError`，整个程序以未捕获异常崩溃退出（`↓` 键因 `min(len-1, ...)` 会意外收敛，但 ↑ 和 Enter 不会）。

### 5. 空目录与 0 字节文件从扫描结果中彻底消失

**位置**：`scan.py` L218（跳过所有目录结果）、L234（`size <= 0: continue`）

没有任何 ≥1 字节文件的目录不会进入树结构（目录仅通过「作为文件的父亲」进入 sizes/contents）。

**实测复现**：删除夹具中某目录下唯一的 4000B 文件后，仍然存在的空目录从 Top-N 报告、CSV/JSON 导出、Web 浏览中全部消失（「共 3 个目录」变「共 2 个目录」）。作为空间分析工具勉强说得通，但目录树完整性受损，且 README 未声明此统计口径。

### 6. 快照锁无陈旧检测 → 进程崩溃后永久锁死

**位置**：`snapshots.py` L444-459（`_acquire_lock/_release_lock`）

锁文件用 O_EXCL 创建互斥，写入了 PID 但从不检查其存活性。保存中途进程被杀 → `.snapshot.lock` 永久残留 → 之后每次保存都报「另一个快照保存正在进行」，只能手工删除锁文件解锁。

## 总结

工程整体质量良好：模块拆分清晰、快照原子写 + CRC 校验、fail-fast 参数校验、Job Object 防孤儿进程等细节用心，单测覆盖也扎实。但：

1. **对比合计重复计数（#1）** 属于核心功能的数值正确性缺陷，用户可直接看到自相矛盾的数字，建议最优先修复（按根行取 total，或明确口径只对叶子求和）；
2. **日配额未接线（#2）** 是「看起来有、实际没有」的保护功能，要么接线要么改文档；
3. **SDK 并发互斥（#3）** 在多线程场景下是定时炸弹，建议让 health/TUI 指纹探测也走 GLOBAL_SCAN_LOCK，或真正启用 dispatcher。

> 附：本报告所有问题的定位均基于源码走查 + 可复现实验；除本报告文件外，测试过程未修改项目任何代码。
