# 产品经理视角 · 体验评审报告

> 评审方式：以真实用户身份完成一次完整 JTBD（Job-to-be-Done）走查，而非功能点测试。
> 工程/质量维度的问题已在《前端测试报告.md》中详述，本文聚焦**产品层**：定位、价值、闭环、增长。
> 评审环境：本次特意修复了 Everything 环境（手动启动主程序后 IPC 就绪），得以走通全部核心路径——这个"修环境"的过程本身就是第一号产品发现。

---

## 0. 一句话总结

这是一个**后端引擎优秀、前端骨架完整、但「信任」与「行动」两环断裂**的产品：数据链路上有一个足以摧毁用户信任的 P0 级数据事故（114688 PB），核心任务闭环在最后一步（对扫描结果采取行动）完全缺失；而它真正的差异化价值（快照 + 历史对比，即"磁盘的时间机器"）反而被埋没在界面角落。

---

## 1. 产品定位速写

| 维度 | 现状 |
|---|---|
| 产品名 | 「Python 磁盘扫描 / PythonDiskScanner」（Web 版单 exe ≈9.5MB 免安装） |
| 目标用户 | Windows 个人用户的磁盘空间清理场景（推断） |
| 核心技术叙事 | 借用 Everything 索引实现秒级全盘扫描（实测 C:+D: 全量约 20 秒，**速度承诺兑现**） |
| 功能面 | 目录浏览排行、空间概览仪表盘、全量扫描、快照保存/撤销、历史对比、一键清空 |
| 明显不做 | 对结果文件的任何操作（删除/打开/导出）、定时快照、主题、多语言 |

**命名问题（低成本高收益的改进）**：把实现语言「Python」放进产品名和数据目录名（`%LOCALAPPDATA%\PythonDiskScanner`），向终端用户传递的是"这是个编程练习"的信号。建议起一个面向场景的名字（如「空间侦探」「DiskLens」「盘查」一类），技术栈不应出现在用户可见层。

## 2. P0：数据可信度事故 —— 「微信聊天记录 114688.00 PB」

### 现象（实测复现）

以真实数据走查时，D:\ 排行第一名显示 **「微信聊天记录 114688.00 PB」**。逐层下钻后找到元凶：`...\msg\migrate\config\` 下 6 个数字命名的小文件，每个被报为 **16384.00 PB**。

`16384 PB = 2^64 字节`（显示值由 `2^64-1 四舍五入而来`）——这是 Everything SDK 在**无法获取文件大小时返回的哨兵值**（0xFFFFFFFFFFFFFFFF）。

### 根因

`scan.py:232` 调用 `Everything_GetResultSize(i, file_size)` 后**未检查布尔返回值**，且过滤条件只有 `size <= 0`——哨兵值是正数，畅通无阻地进入聚合，沿目录树逐级汇总成天文数字。

### 影响面（实测确认，污染整条数据链路）

1. 目录浏览排行 → 第一名 114688.00 PB；
2. 构成环图 → 比例失真；
3. **空间概览仪表盘** → C 盘显示「49152.00 PB」（Users 32768 PB、Program Files 16384 PB），首屏核心模块完全失真；
4. 全量扫描结果与快照 → 坏值落盘；
5. **历史对比** → Top 变化全是「+16384.00 PB +16.67%」的垃圾行，真实信号（如 Star Rail Game +2.25 GB）被淹没。

### 为什么这是 P0

磁盘分析产品的唯一承诺就是"我告诉你的数字是真的"。用户第一次打开就看到超过人类文明总存储量的数字，**不会想到是边界 bug，只会判定这工具不可信然后卸载**。修复本身很小（检查 GetResultSize 返回值 + 对 size 设合理性上限如 16 TB），但必须最优先。

### 附带发现：对比结果的"祖先重复计数"稀释信号

对比表格中同一条增长会以每个祖先目录一行的方式重复出现（D:\ → D:\微信聊天记录 → …\xwechat_files → … 各占一行）。逻辑上没错（父目录确实变大了），但用户视角是"一条变化占六行"。建议提供「仅看叶子变化」开关或按最深目录 rollup，让 Top-N 列表的信噪比提升数倍。

## 3. 激活漏斗：三道墙（实测逐一撞过）

新用户的第一个任务是"让页面右上角变成绿色"。实测发现这道关比想象中难得多：

| # | 墙 | 实测经历 | 建议 |
|---|---|---|---|
| 1 | **硬依赖第三方软件** | 必须先装好 Everything 并完成索引，本产品才有意义 | 安装包引导页直接给 Everything 官网链接+检测按钮；考虑内置 NTFS MFT 直读作为无 Everything 的降级引擎（WizTree 已验证该路线可行） |
| 2 | **Web 版丢了自动拉起能力** | CLI 版有 `env.ensure_everything_running()`（自动启动+等待就绪），**Web 入口没有接入**。本次实测：手动启动 Everything 主程序 4 秒后就绪——说明修复成本极低 | `run_server()` 启动时调用现成的 `ensure_everything_running`；健康徽章加「一键尝试启动 Everything」按钮 |
| 3 | **服务形态安装 = 永久失败且无解释** | 本机正是这种形态：Everything 以服务方式跑在 Session 0，健康检查永远 false，页面只说「尚未就绪」。README 自己都写了要区分 Session 0，但 Web 版没利用这个判断给出针对性提示 | 检测到"仅有 Session 0 实例"时明确提示：「检测到 Everything 后台服务，但需要您打开一次 Everything 主程序」——一句话就能救活大量用户 |

另外两个激活细节：
- 未就绪时首屏自动浏览 D:\ 直接甩出红色错误横幅（详见前端报告 P2-1），应改为引导态；
- 使用指引第 4 步把「一键清空数据目录」当作常规流程教给新用户，危险操作的曝光位给错了——指引第 4 步应该是"第二天再来对比变化"，那才是留存钩子。

## 4. 核心任务闭环断点：产品只能"看"，不能"动手"

用户的完整 JTBD 是：**「C 盘红了 → 找到大头 → 处理掉 → 下次验证没反弹」**。

实测逐步走完前半程体验很好：秒级扫描 → 排行条形图 → 点进目录 → 面包屑回退 → 筛选排序。但走到"处理掉"这一步：

- ❌ 不能右键/按钮**打开所在文件夹**（最起码的行动）
- ❌ 不能**复制路径**
- ❌ 不能删除文件/目录（哪怕回收站方式）
- ❌ 不能导出报告（CLI 有 `--export csv/json`，Web 版完全没有暴露）

这意味着用户必然是：在本产品里**看**→ 打开 WizTree/资源管理器**做**。产品亲手把最有价值的最后一步让给了竞品，而补齐成本极低：「打开所在文件夹」（`explorer /select`）和「复制路径」合计不超过半天工作量，却能把闭环焊上。**这是性价比最高的一笔产品投资。**

## 5. 差异化真价值被埋没：「磁盘的时间机器」

竞品速览：

| 竞品 | 强项 | 弱项 |
|---|---|---|
| WizTree | MFT 直读极快、免费、可删可导出 | 无历史对比 |
| TreeSize | 商业成熟、树状管理强 | 收费、重 |
| SpaceSniffer | 块图可视化直觉 | 无历史、无中文 |
| Windows 存储感知 | 系统内置 | 粗粒度、不可控 |
| **本品** | Everything 秒扫 + **快照 diff** + 中文本地 Web | 依赖重、行动缺失 |

**「上次清理后，这几天什么又在偷偷变大？」——这个问题只有本品能回答。** 实测对比链路可用（选基线→15 秒出结果→汇总卡片+变化条形图+明细表）。这是留存引擎：第一次扫描是获客，第二次对比才是留下来的理由。

但当前产品把它埋在一个自由文本路径输入框里（基线快照路径），普通用户根本不知道填什么。建议：

1. 快照列表每条加「与当前对比」按钮（免输入）；
2. 对比完成后主动提示「7 天后再来对比一次？」（配合定时快照）；
3. 把产品叙事从"磁盘扫描"改写为"给你的磁盘拍快照，看清时间维度上的变化"。

## 6. 其他体验观察（实测记录)

| 观察点 | 现象 | 建议 |
|---|---|---|
| 进度反馈粒度 | 全量扫描进度只有盘间刻度（C 完成=50%），扫 D 盘期间长期停在 50% 平台期 | 加当前盘内已索引条目计数或至少转圈动画+已用时 |
| 概览不自动刷新 | 后台扫描完成后概览面板仍是旧态，需手动点「刷新概览」 | 扫描完成回调里顺带 refreshOverview() |
| 保存的原子性 | 多盘保存是 all-or-nothing：一个盘失败，另一个盘也不保存（本次因测试沙箱限制观察到报错路径，机制本身值得商榷） | 单盘失败不影响其他盘，逐盘汇报成功/失败 |
| 错误文案 | 保存失败时 toast 直接展示 `[Errno 13] Permission denied: 'C:\\\\...'` 原始 OS 错误 | 与前端报告 P1-1 同源：建立用户语言错误映射 |
| 设置面板厚度 | 只有一个自动保存开关 + 数据目录展示 + 清空按钮 | 可补：排除目录列表、快照保留策略、开机自启、深色主题 |
| 版本与反馈 | 页面无版本号、无更新检查、无反馈入口 | 页脚加版本号；本地工具至少留个 GitHub/反馈邮箱 |

*诚实性备注：上述"保存失败"现象经排查是我这边自动化沙箱禁止写 %LOCALAPPDATA% 所致，非产品缺陷（8 月 22 日的正常会话文件可证）；但由此暴露的报错文案与原子性问题在真实故障下同样成立。*

## 7. 若继续迭代：建议的优先级

**P0（信任底线，本周）**
1. 过滤 Everything 尺寸哨兵值（GetResultSize 返回值检查 + 合理上限），修复概览/浏览/对比全链路；
2. 错误文案中文化映射 + 行动指引（含 Session 0 场景专述）。

**P1（闭环与激活，两周内）**
3. 结果行加「打开所在文件夹」「复制路径」；
4. Web 启动接入 ensure_everything_running 自动拉起；
5. 快照列表内一键对比 + 对比结果叶子 rollup；
6. 首屏未就绪引导态替代红错。

**P2（留存与差异化，一个月）**
7. 定时/提醒式快照（Windows 计划任务），把"7 天后对比"做成默认习惯；
8. CSV/JSON 导出入口搬到 Web；
9. 产品更名去 Python 化 + 图标/官网素材统一；
10. 前端 vitest 冒烟测试（见前端报告）。

**若需度量迭代效果，最小指标集**：环境就绪率 → 首次全量扫描完成率（激活）→ 快照保存率 → 7 日对比回访率 → 对比后浏览点击率。本地工具虽无埋点传统，但这五个比率决定了上面每一项投入的先后。

---

## 8. 结论

工程底子（333 个后端测试、原子写快照、并发锁设计）明显超出同类小工具的平均水准，速度卖点也真实成立。但它现在像一个"只管测量不管施工"的仪器：**修好数字（P0）、接上行动（打开/复制/导出）、点亮差异化（一键对比的时间机器叙事）**，就有机会从"又一个磁盘扫描器"变成唯一的"磁盘变化追踪器"。
