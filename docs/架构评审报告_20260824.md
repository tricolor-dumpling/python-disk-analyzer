### 2.3 新发现问题（本轮首次报告）

#### P1

**N-1 浏览请求竞态：迟到响应覆盖新目录**
- api():51-58 裸 fetch 无 signal；browsePath():366-402 无序号 token，await 后无条件渲染。
- 触发链：进入未建索引的深层目录 Y（SDK 实扫分支持 GLOBAL_SCAN_LOCK，秒级~十秒级）→ 等待期间点击缓存盘 chip 回到 X（索引命中毫秒回）→ X 先渲染，Y 的迟到响应随后到达，把面包屑/列表/document.title/lastBrowse 整体拉回 Y。此后「返回上级」「R 刷新」全部基于错误位置。
- 建议：`let browseSeq=0` 进入时 `const seq=++browseSeq`，await 后 `if(seq!==browseSeq)return`；或 AbortController。

#### P2

- **N-2 对比行字段契约漂移**：前端读 `row.baseline_size/current_size`（app.js:735-736），后端实为 `baseline/current`（compare.py:81-87）→ 新增/删除兜底统计是恒死代码，当前碰巧靠 added/removed 布尔位结果正确。
- **N-3 `.stat-path` 类不存在于 CSS**：app.js:743 输出的 class 在 style.css 中 MISS，`.stat-value` 无断行规则；`.compare-summary` 是 minmax(160px,1fr) 网格，超长 Windows 路径（反斜杠无断行机会）会把卡片撑出横向溢出。
- **N-4 一键清空后前端残留态**：wipeData():844-859 成功回调不清 baseline datalist/输入框/lastRoots → 立即对比报「基线不存在」；下次任意浏览经 updateRecentRoots 把旧 roots 写回刚清空的 config.json，违背「配置将恢复默认」承诺。

#### P3

- **N-5** 缓存徽章说谎：browsePath():388 只要 `!data.scanning` 就标「来自内存缓存」，但 SDK 实扫正常响应本就无 scanning 字段 → 刚实扫完也标注缓存。建议后端加 `source:"cache"|"sdk"`。
- **N-6** 日配额拒绝被渲染成红色 error toast（app.py:295-296 → 409 → app.js:580-581），属预期行为应为 info/warn。
- **N-7** undo 部分失败被吞：undeleted[] 非空仍 ok:true（app.py:354-359），前端只报成功。
- **N-8** pollFullscan 五处入口各自 setTimeout 自旋可短暂叠加；catch 分支直接 return 不再续期，网络闪断后进度 UI 停摆（app.js:509-520）。
- **N-9** 深色适配与打印样式零覆盖；saveSettings():827 每次向后端写入死键 `theme:"light"`。
- **N-10** 排行视图长文件名不截断（.ranking-name 无 nowrap/ellipsis），与表格视图 .name 行为不一致，超长名撑高行。
- **N-11** 窄屏 topbar 无 wrap，≲420px 时徽章+按钮溢出裁切。
- **N-12** 相对路径可当浏览根（normalizeRoot 仅 trim；后端按 cwd 解析相对路径）→ 输入 `web` 会静默浏览服务器侧相对目录。建议强制 is_absolute()。
- **N-13** 栅格布局选择器耦合中文 aria-label（`.grid-main>section[aria-label="目录浏览"]`），改文案即静默破坏 8/4 栅格，应改专用 class。
- **内存泄漏维度结论**：未发现真实泄漏（innerHTML 重建、健康轮询单次注册、toast 自清）；pollFullscan 多链路是叠加非泄漏。

### 2.4 后端功能与健壮性（面板问题背后的服务端根因）

- **路由契约**：12 条路由形态统一（ok/error + 中文消息），截断策略 browse 200/overview 10/compare 100 且 browse 带 total——设计合格。但 compare 的 `truncated` 反映底层 500000 行截断而非 100 行切片（app.py:421 + compare.py:92-95），语义误导；无 API 版本化；404/405 是 HTML 页与 JSON 契约不一致。
- **B-1【P2】保存的半原子性产生孤儿快照**：`_save_fullscan_result`（app.py:263-293）循环保存多盘，第二块盘抛异常时第一块盘的快照已落盘且台账已更新，但 session 清单尚未写出 → 该快照成为孤儿：Web 快照列表（session 驱动）看不见它，UI 无法撤销，只能手动删文件。建议：先写全部临时产物再统一提交，或逐盘汇报成功/失败并在响应中如实列出。
- **B-2【P2】撤销不回滚台账**：api_save_undo 只删快照文件+session（app.py:336-352），ledger 的 `last_fingerprint` 保持保存时的值 → 撤销后磁盘内容没变，下一次自动保存被「指纹未变」谓词静默抑制，直到磁盘再次变化。撤销语义不完整。
- **B-3【P2】compare 静默使用过期缓存当"当前"**：api_compare 优先取 fullscan.result()（app.py:400-404）——那可能是任意久之前的全量结果，用它对比基线产生的 diff 用户无从知晓时效。至少应在响应中透出 completed_at 并由前端展示。
- **B-4【P3】`tree_complete=auto` 误导性传参**：app.py:272 把 auto 值塞给 tree_complete；save_snapshot 内部该参数只在 auto=True 时参与谓词（snapshots.py:555-565），显式保存下传 False 无效果——不是功能 bug 但是阅读陷阱，应显式传 True 或删除。
- **B-5【P3】session.save_session 裸 write_text**（session.py:69-72），与 snapshots/台账的 tmp+os.replace 原子纪律不一致，崩溃窗口内可产生半截清单（Web 列表按清单驱动，半截清单=load_session 返回 None 静默消失）。
- **B-6【P3】扫描期间非活动盘一律 409**：api_browse 分支②（app.py:154-181）对"不在索引、也不在当前扫描盘"的目标（如扫 C 时浏览 E:\）返回「请等待完成后再浏览」，而设计原则的三级策略第③级（SDK 回退）永远不可达；且回退若放行会阻塞在 GLOBAL_SCAN_LOCK 上直到全量结束——两难但现状最差：既不能看也不说明要等多久。建议 409 文案附预计剩余时间，或提供排队选项。

### 3.2 缺口分级明细

- **G-1 导出（P1）**：《产品经理体验评审》已指出这是核心闭环断点之一。补齐成本低：`GET /api/export?format=csv|json&root=X` 复用 cli.export_report_csv/json（cli.py:510-541）几乎零改动；数据源直接用 fullscan.result(root) 的 rows。
- **G-2 自动拉起（P1）**：run_server 内 bind 前调用 ensure_everything_running，捕获 EverythingEnvironmentError 降级为日志+/api/health 透出原因（不要学 CLI 致命退出）；顺带补 init_windows_job_sandbox 保持对称。这是激活漏斗三道墙中成本最低的一堵。
- **G-3 Session 0 提示（P2）**：health 响应加一个 `service_only:true` 字段（env 已有 session-id 判定能力），前端黄条改文案即可救活大批用户。
- **G-4 快照目录（P2）**：设置页加快照目录展示+修改（落 config 新键并由 get_snapshot_dir 读取，或维持 env 方案由后端 setenv）。

## 四、检查点③：架构师补充检查

### 4.1 数据可信度（P0，最高优先）

**S-1 哨兵值事故未修，且口径不一致扩大到 3 处**：
- 主扫描 scan.py:232-234：GetResultSize BOOL 返回值被忽略，仅 `size<=0` 过滤（哨兵 2^64-1 为正数畅通）；
- 轻刷 scan.py:455-457：**连 size<=0 过滤都没有**（同一项目两种口径）；
- dispatcher._execute dispatcher.py:299-305：`int(size.value)` 无过滤（虽然 dispatcher 未接线，但属于同一地雷）。
- 附带疑点：scan.py:234 把真实 0 字节文件也从聚合剔除（父目录少计 0 字节本身无害，但「纯零字节文件的目录不进 sizes」会使目录计数偏小）——如非有意应一并修正。
- **修复建议**：封装 `read_result_size(everything,i)->int|None`（BOOL FALSE → None；size==0xFFFFFFFFFFFFFFFF → None），三处共用；None 不计入聚合但在 UI 上标注「N 条大小未知」。这是信任底线，一行封装函数的成本。

### 4.2 安全（本地单用户模型下按实际风险排序）

- **SEC-1【P2】settings POST 无白名单 + 配置投毒链**：app.py:447 `config.update(data)` 任意键合并落盘；而 CLI 启动链信任 config 的 everything_exe/everything_startup_args 去 Popen（env.py:183,463,470-473）——Web 端写入的脏键会被未来的 CLI 启动消费。DLL 路径有 base_dir 校验（sdk.py:71），exe 路径没有。建议固定键白名单，`everything_*` 键拒绝从 API 写入。
- **SEC-2【P2】browse 任意路径 + 无 Host 校验**：绑定 127.0.0.1 下同机进程本拦不住，真正增量面是 DNS rebinding 读全盘目录树。一行 Host 白名单中间件封掉。
- **SEC-3【P3】CSRF 面**：JSON POST 被 Content-Type 预检挡住，但 /api/fullscan/start 无 body 可被跨站 no-cors 表单静默触发（骚扰级）。启动期生成 token 注入页面+API 校验可整体关闭。
- **SEC-4【P3】undo 无路径包含性校验**（app.py:337-347 直接 unlink 清单里的路径），篡改清单可删任意文件（前提已是本机写权限，故 P3）。unlink 前 `relative_to(get_snapshots_dir())` 校验。
- **✅ 通过项**：wipe 边界固定数据目录、symlink 不追目标、扫描中拒绝；debug=False 无堆栈泄漏；esc() 前端转义一致。

### 4.3 并发与线程

- ✅ 锁纪律总体良好：_STATE_LOCK 护全部状态、GLOBAL_SCAN_LOCK 串行化 SDK、BrowseIndex RLock 分片锁外构建+单赋值发布、双标签并发提交不会双开（start 锁内双检）。
- **C-1【P3】TOCTOU×2**：overview 先读 result 再查 index 的间隙撞上新扫描 clear() → benign 的 invalid_index；compare 的 is_running 检查与拿锁之间若扫描启动，请求线程阻塞至全量结束（分钟级挂起 Werkzeug 线程）。建议拿锁失败立即 409。
- **R-2【P2】停服硬杀扫描线程**：daemon=True 无 atexit/signal 收尾，cancel_event 从不传入 Web 链路（fullscan.py:264-266）——丢进度但不损盘（快照写在请求线程且有原子替换）。建议 atexit 置位 cancel_event + join(timeout)。

### 4.4 内存与容量

- **R-1【P2】实测与推算**：本次评审实测——完成 C 盘(13 万目录)+D 盘(6 万目录)全量后，服务进程私有内存 **~768MB**（约 19 万目录 rows + BrowseIndex 双份驻留）。结构上 display_paths 是纯冗余（可由 key 推导，fullscan.py:54-55），rows 与索引字符串不共享。外推百万目录盘 >0.5GB/盘，多盘叠加无上限保护。
- **能扫不能存**：MAX_ROWS=500_000 超限抛 ValueError（snapshots.py:524-527）→ 被包装成 409「保存 X 快照失败」，超大目录数的盘保存必失败且文案不说明真因。建议：砍 display_paths、rows 共享引用、超限时报「目录数超过 50 万上限」。

### 4.5 部署与打包

- **DEP-1【P2】端口占用零防护 + 双实例静默共存**：本次实测踩实——端口 5000 同时出现两个 LISTENING 进程（Windows 下 werkzeug SO_REUSEADDR 允许双绑），新起的实例成为「永不接客」的隐形僵尸，console=False 打包下用户完全无感知；Timer(0.8s) 开浏览器还先于 bind。建议 bind 前探 `/api/health`：通则视为已在运行直接开浏览器退出。
- **DEP-3【P3】spec excludes 含 `'concurrent'`**（python-disk-scanner-web.spec:107）：今天安全只因 Web 不 import dispatcher；将来接入 dispatcher（concurrent.futures）打包版即 ImportError 崩溃。需注释联动或改排除粒度。
- ✅ PyInstaller 其余适配自洽：windowed stdout=None 兜底、frozen 路径、DLL 随包拷贝、templates/static datas 打包均正确。
- 【P3】exe 无版本信息资源（spec 无 version= 块）+ 页面无版本号 → 用户无法报告自己用的版本。
