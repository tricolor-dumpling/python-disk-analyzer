## 一、任务与根因（已在 P3 交付后的代码上重新核对行号）

### 问题 5（对比直接显示最深目录，用户要"深度选择 + 聚合 + 下钻"）

确认缺口：

- 后端两条路径都写死叶子口径：`app.py:910-918`（缓存命中/异步提交路径）与 `app.py:984-996`（同步路径）均为 `compare.diff_from_current(..., leaf_only=True)` + `rows = compare.top_growth(report, 100)`。
- `compare.py:130 _merge(b_map, c_map, leaf_only=False)` 无 depth、无 rollup；`compare.py:101 _leaf_keys(keys)` 只回答"是不是叶子"。
- `compare.py:199 compare_snapshots(..., leaf_only=False)`、`compare.py:255 diff_from_current(..., leaf_only=False, ...)` 均为透传。
- 前端 `web/static/js/app/pages/compare.js` 无任何深度控件；结果表直接呈现后端返回的 100 行叶子。

后果：结果只列 `D:\Clash for Windows\resources\static\files\default` 这类最深叶子，用户无法先看"某层目录的总增量"。

### 问题 6（没有增量时也列出 0 增量目录）

确认缺陷，三个独立成因：

- `compare.py:142-159` 对两侧键并集每键都产行（delta 可为 0）；
- `compare.py:249 top_growth(compare_result, n=10)` 按有符号 delta 降序 → 零行排在所有正增量之后、负增量之前：正增量 <100 条时零行补位，零行 ≥100 条时负增量（可释放空间）被整段截断；
- 前端：全量入表、仅在 `rows.length === 0` 时显示"无差异"、摘要卡只统计切片内 rows（与 `delta_total` 口径自相矛盾）。

### 与计划文档的一处出入（以代码为准）

计划第十章写「top_growth 被 cli.py:518、tui.py:593 共用」。实测 **tui.py 不调用 top_growth**——它在 `tui.py:593`、`tui.py:608` 直接调 `compare.diff_from_current(...)` 并遍历 `diff_result["rows"]`（`tui.py:635`）。因此：

- `top_growth` 的调用方 = `cli.py:518` + `app.py:918/996`；
- `diff_from_current` 的调用方 = `cli.py` + `tui.py:593/608` + `app.py:910/984` + 测试。

「默认行为不变」这条红线对 `diff_from_current` 与 `top_growth` 同等适用（TUI 历史对比模态 D8-H 直接吃 `diff_from_current` 的 rows）。

## 三、设计决策（计划 D4-1…D4-6，直接执行）

- **D4-1 聚合放在后端 `_merge` 内、排序/截断之前**。理由：前端聚合只能处理"已被 top-100 截断"的叶子行，上层目录增量会被严重低估。
- **D4-2 参数语义**：`/api/compare` 新增可选 `depth`（int，≥1；缺省/null = 现状叶子口径）。不传时响应任何字段的值逐字节不变。
- **D4-3 零增量**：后端在排序/截断之前过滤 `delta == 0`；排序支持"按 |delta| 降序"以让正负增量都能进榜。`top_growth` 新增参数（如 `min_abs_delta` / `order_by`），默认行为一字不改。
- **D4-4 空态判据**：前端"无差异"必须基于过滤后的行集合，不得再用原始 `rows.length`。
- **D4-5 摘要口径**：摘要卡（总变化 / 最大增长 / 可释放）必须基于未截断的全量聚合行——后端 additive 返回 `rows_total` / `zero_count` / `max_growth` / `max_release` / `depth`，消除与 `delta_total` 的自相矛盾。
- **D4-6 下钻交互**：行点击 = 页内下钻（以该目录为新根重新对比/聚合）+ 面包屑返回。不选"跳工作台浏览"方案（与用户"支持进入更深目录"的诉求不符）；选择结果写入交付报告。

## 四、硬性约束与红线

1. **向后兼容红线**：不传 depth 时 `/api/compare` 响应与 v2.0.0 完全一致——用直调引擎逐字段相等的契约用例证明，不接受"看起来一样"。

3. 禁止用前端过滤替代后端"切片前过滤"——那会掩盖"负增量被挤出 top-100"这一真实缺陷（问题 6 的核心）。

10. 不触碰 Everything 进程与用户自带 Edge；不按镜像名批量杀进程。
11. **Git**：一变更集一提交；提交信息 `阶段P4变更集N：<内容>（<关键文件>）`；禁止 `push --force`、禁止改写已发布历史；禁止提交 `%TEMP%` 产物与 `_p4_progress.md`。
