# 文档索引与管理规范

本文件回答四个问题：**仓库里有哪些文档、各自管什么、什么时候必须更新、什么时候该删**。
内容类事实（文件职责、API、界面契约）在 `README.md`；约束类在 `AGENTS.md`；操作流程在 `docs/开发规范.md`。
本文件只做**索引与治理**，不重复它们的内容。

## 2. 文档分级（决定放哪、留多久）

| 级别 | 判据 | 落点 | 寿命 |
|---|---|---|---|
| **长期** | 后人/agent 不读就会做错事 | `README.md`、`AGENTS.md`、`docs/` 下的参考文档 | 随项目 |
| **过程** | 只对当前这次开发有意义（进度、临时结论、中间稿） | `tmp/`（不入库） | 用完即删 |
| **记录** | 事后追溯用（做了什么、怎么验的） | `docs/CHANGELOG.md` | 永久追加，不删只增 |
| **禁止入库** | 运行数据、凭据、一次性核查脚本 | 真实数据目录 / 环境变量 / `tmp/` | — |

**判定口诀**：一句话能写清、且写错会让人踩坑 → 进 `docs/`；
需要展开成多页方案、或只对本次开发有效 → 进 `tmp/`，定稿后把结论浓缩进 `docs/`。

## 3. 更新与淘汰规则

**必须更新**（与 `docs/开发规范.md` 第 3 节清单一致，此处只列文档侧）：

1. 动了文件 → `README.md` 文件职责总表（`tests/test_docs_sync.py` 会红）；
2. 动了路由或响应字段 → `docs/API 契约.md` + `tests/test_api_contract.py`；
3. 立了新红线 → `AGENTS.md` 第 3 节；
4. 改了流程 → `docs/开发规范.md`；
5. 定位了一个新坑 → `docs/排查手册.md`；
6. 每次开发完成 → `docs/CHANGELOG.md` 追加一条；
7. 本文件：新增/删除/改名任何**文档** → 更新第 1 节清单。

**淘汰规则**（避免文档腐化成误导）：

- 内容已被代码结构取代 → **删除**，不要留「已废弃」段落（历史考古走 `git log`）；
- 同一事实出现两处 → 保留一处、另一处改为链接（**禁止双份**）；
- 长期无人维护且已不可信的参考文档 → 删除并在 `docs/CHANGELOG.md` 记一条原因；
- `tests/test_docs_sync.py` 报「僵尸条目」= 文件已删而总表没同步，属必须立即修的红灯。

## 3.5 文档按需自动生成（不必先问）

开发中一旦触及**尚无文档覆盖的领域**，**直接生成**，不要问、也不要塞进不合适的地方：

| 触发条件（出现即生成） | 生成什么 | 权威落点 |
|---|---|---|
| 引入新的**外部依赖 / 运行前提 / 环境变量** | 更新 `README.md`「运行环境」+ `AGENTS.md` 第 6 节 | README（内容类） |
| 新增一类**用户可见行为**或界面语义契约 | `README.md`「界面契约」新增条目 | README |
| 新增**可数事实**（路由数、键位数、清单项、阈值常量） | 用 `DOCFACT` 标记包裹 + 在 `tests/test_docs_consistency.py` 的 `FACT_CHECKS` 加检查 | 该事实的权威文档 |
| 出现**需要多段解释**的领域（新子系统、新数据格式、新协议） | 新建 `docs/<主题>.md` | 新文档自身 |
| 出现**新的失败模式**（踩坑并定位了） | `docs/排查手册.md` 追加一条症状 | 排查手册 |
| 出现**新的约束/红线** | `AGENTS.md` 第 3 节（并同步 DOCFACT 计数） | AGENTS.md（约束类） |

**生成时的四步**（缺一步就会被测试拦下）：

1. 复制 [`docs/_文档模板.md`](_文档模板.md)，补齐「职责 / 权威来源 / 更新触发 / 唯一性声明」四要素；
2. 登记进本文件第 1 节**文档清单**（否则索引失联）；
3. 登记进 `README.md` 的「项目文档」文件表（否则 `tests/test_docs_sync.py` 红）；
4. 跑 `.venv\Scripts\python.exe -m pytest tests -q` 确认两套文档契约全绿。

**命名约定**：`docs/<主题>.md`，用中文主题名或大写专有名词；**下划线开头**（如 `_文档模板.md`）表示
模板/内部文件，不参与索引编号。**禁止**把长期内容写进 `tmp/`（那是不入库、可随时整体删除的临时区）。

## 3.6 文档冲突判定（不许冲突）

**根本原因**：同一事实写两遍，迟早只改一处 —— 两份说法就开始互相矛盾。所以：

### 单一权威原则

一个事实只能有**一处权威定义**；其它文档一律写成**链接或引用**，不得复述成第二份。
`tests/test_docs_consistency.py` 机械执法：非 README 文档里若出现「文件职责表」，直接判红。

### 冲突时的优先级（自高到低）

| 级别 | 来源 | 说明 |
|---|---|---|
| 1 | **可执行事实**：代码、`tests/` | 最高权威。文档与代码不符 = 文档错 |
| 2 | `README.md` | 内容类冲突（文件职责、API、界面契约）以它为准 |
| 3 | `AGENTS.md` | 约束类冲突（红线、编码约定）以它为准 |
| 4 | `docs/*.md` | 参考类，与上面冲突时一律让位 |

**处置口径**：冲突时**改文档、不改测试**（除非确实要改行为——那就先改代码与测试，再同步文档）。
若某文档只是摘要（如 `docs/API 契约.md`），必须在开头写明**权威在哪**，并声明「冲突时以权威为准」。

### 三种冲突与拦法

| 冲突类型 | 例子 | 拦截者 |
|---|---|---|
| 同一职责写两遍 | 两个文档各有一张「文件职责表」 | `TestNoDuplicateResponsibility` |
| 幽灵引用 | 引用了已删除/改名的文件 | `TestNoDanglingReferences` |
| 数值失真 | 文档写「19 条路由」而代码是 18 条 | `TestDocumentedFactsMatchCode`（`DOCFACT`） |
| 时间倒序 | 新记录插到了 CHANGELOG 中间 | `TestChangelogDiscipline` |

## 4. 当前文档欠账（已知缺什么）

诚实登记未写但**已知有价值**的文档，避免「以为都齐了」：

| 缺口 | 为什么值得写 | 现状替代 |
|---|---|---|
| 架构决策记录（ADR） | 「为什么这么设计」目前只散落在源码注释里（如 `P12·W1.1` 之类的阶段标记），新人无法还原取舍 | 源码注释 + `docs/CHANGELOG.md` 的历史阶段索引 |
| legacy 快照迁移指引 | 历史快照中存在大小 ≥ 16 TiB 的「已知异常大小」行（旧版 Everything 语义），会拉偏合计；何时该重扫重建基线尚无成文指引 | `snapshots.py` / `compare.py` 的 `_LEGACY_SIZE_THRESHOLD` 注释 + 界面提示 |
| 部署与多实例运维说明 | 防双实例探测、端口占用、协作停服、Job Object 防孤儿的运维面向说明 | `app.py` 启动段注释 + `tests/test_shutdown.py` |
| 发布产物校验清单 | 发版后的外部校验步骤目前只在 `AGENTS.md` 第 8 节，可拆成可勾选清单 | `AGENTS.md` 第 8 节 |

> 这些**不是必须马上写**——写文档的成本要用「不写会不会让人做错事」来衡量。
> 需要时按上面「更新与淘汰规则」新增，并同步登记进第 1 节清单。
