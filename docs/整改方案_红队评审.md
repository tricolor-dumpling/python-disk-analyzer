## 【总体判定】有条件放行

草案对第一轮输入的整合忠实度高：11 项冲突裁决全部有着落，§六八项遗留全部吸收，DEF/D/N 编号体系与源码行号抽查基本准确（见文末确认清单），批次划分与工作量自洽，护栏设计（回归先行＋两条红线＋独立提交）方向正确。**但存在 7 个必须在修订版解决的阻塞项**：两个是「修法落点写错文件会导致 P0 验收直接失败」的正确性风险（RT-01/RT-02），一个是台账与测试现状脱节（RT-03），四个是「修法要点漏掉关键契约细节、实现者按字面做必然破坏既有调用方」（RT-04/05/06/07）。这些都不动摇方案骨架，修订成本约半天。

### RT-01 合计口径修复落点错位：三条生产对比链路走的全是 diff_from_current，不是 compare_snapshots
- **位置**：草案 W1.2（修法要点引 §四#1）；compare.py:148-149（compare_snapshots）、**compare.py:187-188（diff_from_current）**。
- **问题**：生产上没有任何调用方使用 compare_snapshots——CLI `--baseline`（cli.py:62,462,470）、Web `/api/compare`（app.py:413）、TUI H（tui.py:571）三条链路全部经 diff_from_current 取合计。§四#1 文字只描述了「合计取根行 total（多根顶层求和回退）」的语义，未点名函数；W1.2 触碰文件虽列了 compare.py，但实现者按字面改 compare_snapshots 即可「完成工作项」而三个出口的重复计数原样保留，P0-2 验收①②③④全灭。DEF-002 台账明明引了 ：187-188，整合时却丢了。
- **建议修法**：W1.2 修法要点改为「合计计算下沉为公共助手，diff_from_current 与 compare_snapshots 两处同步替换」；验收追加⑤「TUI H 视图合计与 CLI/Web 同输入一致」。

### RT-02 health busy 语义没有前端契约，W2.1 落地即制造新回归
- **位置**：草案 W2.1（health 非阻塞 acquire+busy）、W1.3（ready 门控/引导态）；fullscan.py:258（`with GLOBAL_SCAN_LOCK:` 包住整个多盘扫描循环）、app.js:146-157（refreshHealth，:1029 每 15s 轮询）、app.js:813-821（设置弹窗健康栏）、app.js:1019-1027（init 门控点）。
- **问题**：全量扫描期间 GLOBAL_SCAN_LOCK 被后台线程全程持有（分钟级），W2.1 后 `/api/health` 在此期间**必然**返回 busy/ready=false。前端三处消费点均未定义 busy 分支：①徽章每 15s 轮询会把扫描中打成 warn「未就绪」；②设置弹窗健康栏显示误导文案；③更严重的是 W1.3 的「ready=true 才自动浏览否则引导态」若随轮询周期求值，一次全量扫描就能把整页打回引导态。草案所有工作项（含 W2.5/W2.6 前端批）都没有接 busy 字段。
- **建议修法**：在 W2.1 验收补一条硬性契约——「busy ≠ 未就绪：徽章保持现有状态并显示『扫描中』中性提示；引导态/自动浏览门控只在首次加载与用户点击『重试环境检测』时评估 ready；设置弹窗健康栏透出 busy 原因」。对应冒烟页加第④断言。

### RT-03 DEF-030 与「419 底线」建立在不存在的测试文件上
- **位置**：草案 W2.12（触碰文件「test_web.py(with-resp)」）、台账覆盖度声明「29 项落地」、§五.1、§八.1「沿用 419 全绿底线」；tests/ 实测。
- **问题**：实测 tests/ 仅 8 个文件（__init__.py、test_cli/test_env/test_export/test_scan/test_sdk/test_tui/test_utils.py），**无 test_web.py、无 test_dispatcher.py**；`def test_` 计数约 165，远低于 419（419 来自架构评审当日的机器，彼时 test_web.py 尚在，见架构报告 §4.7）。因此：DEF-030（test_web.py:70,73 ResourceWarning）的修复对象不存在，W2.12 引用它属于幻影工作项，「29 项落地」虚高；「419 全绿」在当前树上无从谈起。草案 §五.1 虽写了「执行首日核对基线」，但没有把后果落到台账和 W2.12 上。
- **建议修法**：①DEF-030 改判：「对象不存在 → 关闭缺陷形态，转为新增 web 契约测试的编码规约（with-resp/close ＋ `-W error::ResourceWarning` 合并门禁），随 W1.0 新建测试生效」；②台账改「28 项落地＋1 项转规约」；③W1.0 交付物显式包含「记录 discover 实际用例数，回填 README D3，并把《开发方案》『419 全绿底线』措辞改为『全绿底线（基数以 W1.0 记录为准）』」。

### RT-04 「N 条大小未知」没有定义传出通道，最顺手的实现会同时炸掉四个调用方
- **位置**：草案 W1.1；scan.py:154-161（返回二元组契约）、fullscan.py:264、tui.py:470、app.py:186、app.py:408、cli.py:392（六处按 `(sizes, contents)` 解包）。
- **问题**：scan_via_everything_sdk 返回二元组是全项目最宽的接口契约；「None 不聚合、UI 标注 N 条大小未知」要求把未知计数送出扫描层，但草案未指明机制。实现者最自然的做法是改返回三元组——fullscan/tui/app/cli 四个模块同一批崩，恰好撞上自己定的「已有字段语义不破坏」红线。另外轻刷路径（light_refresh）的调用方 tui.py:492 也需要展示口径，未提及。
- **建议修法**：W1.1 明确零破坏通道并写死（推荐：返回的 sizes dict 附加 `unknown_size_count` 属性，或 LazyContents 挂元数据，或 scan 模块级 last_scan_stats）；golden 夹具覆盖「含未知条目→计数正确、聚合不含、二元组解包不变」；补一句轻刷侧的展示口径。

### RT-05 存量哨兵污染快照无任何处置路径，而风险表引用了不存在的 scrub 机制
- **位置**：草案 §七「快照相关变更伤及老用户数据」一行（「quarantine/scrub 触碰坏快照…scrub 需显式 flag」）；输入汇总 §四#5（BE 原方案含 quarantine 改名＋CLI --scrub-snapshots）；W1.1-W3.5 全部工作项（均无此项）。
- **问题**：BE 第一轮方案的坏快照清洗工具在整合时被静默丢弃，§七 却仍把它当作既有缓解措施引用——风险登记表出现了指向虚空的控制措施。后果本身也真实：修复上线前落盘的快照若含 2^64-1 行，新合计逻辑会忠实算出天文 delta，用户在「修复后」的版本依然看到 114688 PB 级对比数字，直接违背目标句。
- **建议修法**：二选一并写进方案：a) 最小检测版（推荐，S）：load_snapshot/_rows_to_map 对 `s ≥ 16TB` 的行打 legacy 标记，对比摘要卡与导出头部提示「基线含已知异常数据，建议重扫重建基线」；b) 恢复 BE 原案的 `--scrub-snapshots`＋quarantine（注意 quarantine 改名会使 session 清单内 snapshot_path 失配，undo/列表需联动，这也是它当初被砍的可能原因——若选 b 必须写联动）。无论选哪项，同步修订 §七 该行措辞使其与工作项一一对应。

### RT-06 P0-3 验收②「≤15s 徽章变绿」与代码自身常量冲突，属不可度量承诺
- **位置**：草案 W1.3 验收②、§九拍板项3；env.py:51（DEFAULT_EVERYTHING_STARTUP_TIMEOUT_SECONDS=20）、env.py:386-405（wait_for_everything_ipc 每 0.5s 轮询至 20s 超时）、env.py:464-487（最多三组启动参数逐一尝试，每组各等 20s）。
- **问题**：自动拉起链路里 IPC 就绪等待上限就是 20s，Everything 冷库加载在慢盘/大索引机器上常态超过 15s；按现文案验收，测试者在正常机器上就会得到「不合格」，门槛不可复现。这正是拿去拍板的 P0 标准，不能带病上会。
- **建议修法**：改为「拉起后 ≤15s 内徽章进入**确定态**：就绪变绿，或进入『Everything 正在加载索引（最长约 20 秒）』的进行时提示；IPC 就绪即刻变绿」。同时引导态文案标注等待上限，避免用户在 15-20s 空窗期重复点击。

### RT-07 显式保存软警告的回传通道未定义，易破坏 save_snapshot 返回契约
- **位置**：草案 W2.2（冲突2 裁决「explicit 超限＝软警告继续写」）；snapshots.py:512（docstring 契约：返回 Path｜None）、tui.py:592-602（S 键按 None 分支）、cli.py 退出保存链、app.py:266-286。
- **问题**：现契约只有「Path=成功／None=auto 被拒」两个值，explicit 永不返回 None。「超限但继续写」的警告需要一个新回传位，草案没说放哪；实现者顺手把返回值改成元组/dataclass 就会破坏 TUI/CLI/app 三处调用方与既有单测。
- **建议修法**：指定 additive 方案，例如模块级 `last_save_notice`（保存后读取即清除）或可选 out 参数，保持返回值不变；README/app 提示消费它；test_tui 补「explicit 超限→保存成功且有警告」断言。可与 RT-04 合并为护栏红线的一条实施细则。
