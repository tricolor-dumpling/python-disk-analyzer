# 问题整改阶段开发计划与标准流程

> 版本：v1.0  
> 状态：规划阶段，尚未开始修改业务代码  
> 依据：`问题说明.md`、`问题逐项核查报告_待修复.md`、`问题核查复现与修改定位清单.md`、现有 `P12_开发执行手册.md` 与 `开发方案.md`。  
> 原则：先确认问题和需求，再按阶段实施；每个阶段必须完成“设计 → 实现 → 测试 → 验收 → 文档更新 → DoD/回滚”，不得以静态代码检查替代真实流程验收。

## 一、总体阶段划分

| 阶段 | 名称 | 覆盖问题 | 目标 | 依赖 |
|---|---|---|---|---|
| R0 | 基线、需求冻结与测试隔离 | 全部问题的前置工作 | 固定版本、确认现象、建立安全测试环境 | 无 |

### 阶段依赖图

```text
R0 基线/需求冻结/隔离
 ├─ R1 数据、状态、缓存、导出
 │   ├─ R2 快照与趋势
 │   └─ R3 自动扫描与进度
 └─ R4 目录关系与视图
     └─ R5 动画/主题/设置/交互
R1-R5 ──> R6 全量回归与发布
```

> R2、R4 在 R1 的稳定接口完成后可并行；R3 必须等自动扫描需求决策完成；R5 必须在视图 DOM 和状态契约稳定后实施。

## 二、所有阶段统一标准开发流程

每个阶段都必须按以下顺序执行，并在阶段文档或进度日志中留下证据。

### 1. 设计

- 明确问题编号、用户场景、成功标准和不在范围内的内容；
- 明确数据来源、字段契约、状态机和失败态；
- 明确触碰文件、依赖、风险、兼容性和回滚方式；
- 涉及 `scan.py`、`compare.py`、`snapshots.py` 或已有 API 时，先写护栏测试设计；
- 涉及删除、清空、自动保存时，先确定安全边界和误操作恢复方案。

### 2. 实现

- 以最小改动实现单一阶段目标；
- 一项工作一个分支/变更集，禁止把无关 UI 美化混入功能修复；
- 保持快照 `format v1`、`(sizes, contents)` 返回结构和已有 API 字段语义兼容；
- 新字段只允许 additive；
- 不使用真实用户快照目录做破坏性开发测试。

### 3. 测试

至少执行适用的测试层级：

1. 单元测试：状态机、数据口径、路径校验、序列化和错误分支；
2. API 契约测试：状态码、响应字段、异常响应；
3. 前端逻辑/页面冒烟：渲染、按钮、路由、loading 收敛；
4. 集成测试：扫描→浏览→保存→对比→导出→撤销；
5. 真实浏览器测试：截图、Network、控制台、动画和窄屏；
6. 破坏性流程：仅在隔离数据目录中执行。

### 4. 验收

- 按本阶段验收清单逐条执行；
- 记录实际命令、版本、端口、PID、输入数据、响应、截图和日志；
- PASS、FAIL、BLOCKED、未覆盖必须明确区分；
- 不能用“代码看起来正确”作为验收结论；
- 若失败，回到设计阶段修订，不得直接标记完成。

### 5. 更新文档

- 更新本计划阶段状态；
- 更新《问题逐项核查报告_待修复.md》的状态和证据；
- 更新《问题核查复现与修改定位清单.md》的复现/验收记录；
- 更新 `docs/开发方案.md` 进度日志；
- 登记遗留问题、需求决策和已知限制。

### 6. DoD 与回滚

阶段完成必须同时满足：实现、测试、验收、文档、回滚方案五项齐全。任何一项缺失只能标记“部分完成”。回滚应能通过撤销该阶段独立变更集恢复，不得依赖手工猜测。

### 统一门禁命令

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -t . -v
.venv\Scripts\python.exe -W error::ResourceWarning -m unittest discover -s tests -t .
node --test scripts/dev/*.test.mjs
.venv\Scripts\python.exe -m py_compile app.py cli.py datadir.py env.py sdk.py scan.py tui.py utils.py exceptions.py keyrouter.py messages.py snapshots.py compare.py fullscan.py session.py main.py
```

真实 Web 验收还必须记录：服务实际 URL、是否复用旧实例、浏览器控制台错误、Network 请求、截图和关闭服务结果。

# 四、R1：数据、扫描状态与缓存可信度

## 阶段信息

- 覆盖问题：1、7、9、13、14、16、17、20、21。
- 关键目标：任何对比/扫描请求都必须收敛到成功、失败、中止或超时；缓存来源不得靠字段缺失猜测。
- 主要定位：`app.py`、`fullscan.py`、`scan.py`、`web/static/js/app/components/scan.js`、`workspace.js`、`api.js`。

## 设计

定义统一状态：`idle/running/stopping/completed/aborted/error`，为每次扫描保留 `scan_version`、开始时间、完成时间、当前盘、完成盘数、停止原因。浏览响应增加兼容性 additive 字段，例如 `source: cache|scan|sdk` 和来源时间；旧字段保留。对比 loading 必须有成功/失败/409/超时收敛路径。轮询要求单链、可停止、页面销毁不叠加。

## 实现步骤

1. 梳理第一次扫描、第二次扫描、停止后的状态生命周期；
2. 为对比请求补充超时/错误收敛和按钮恢复；
3. 统一 `/api/fullscan/status` 轮询入口，统计请求频率；
4. 将浏览缓存徽章改为读取后端明确 `source`；
5. 核查停止后 `result_ready/save_ready/BROWSE_INDEX` 的一致性；
6. 为导出入口统一无结果、扫描中、部分结果、完成结果文案；
7. 配置 Web 日志策略，区分必要错误、开发 access log 与 CLI 启动日志；
8. 排查 health 的 `busy` 是否与真实全量扫描一致，补 Session 0/IPC 诊断。

## 测试

- 第二次连续扫描状态版本递增且最终收敛；
- 停止请求返回后最终进入 aborted，`stop_reason=user`；
- 对比 loading 不会永久存在；
- 同一路径分别从内存索引、SDK、全量扫描结果返回正确 source；
- 导出 CSV/JSON 的成功和保护错误契约通过；
- 30 秒轮询日志无重复轮询链、无异常堆栈；
- health 直接 test_client 与正式 run_server 的编码行为均可解释；
- 浏览器控制台无未处理 Promise 和运行时错误。

## 验收

使用 R0 夹具执行：首次扫描→完成→第二次扫描→中止→再次扫描→浏览→对比→导出。记录每秒 status、Network、toast、状态栏和缓存徽章。验收标准：请求均有终态；停止有即时“正在停止”和最终“已停止”；真实 SDK 结果不显示缓存；扫描中日志可解释；导出在完成状态可下载。

## DoD/回滚

DoD：状态机、缓存来源、导出和日志均有契约测试与集成证据；无旧 API 破坏。回滚：按 R1 独立变更集回退，恢复原轮询和徽章逻辑。

# 五、R2：快照管理与历史趋势闭环

- 覆盖问题：3、4。

- 前置：R0 夹具；R1 稳定快照/状态口径。

## 设计

先确定删除粒度。若支持单盘删除，必须同时处理快照文件、session 条目、ledger 和最近对比缓存；若支持整会话删除，必须明确多盘原子性和部分失败反馈。删除接口必须做快照目录边界校验、路径规范化、并发保护和幂等处理。趋势卡口径固定为同盘、较昨日 `0<Δt≤24h`，较上周 `24h<Δt≤7d`；无基线必须显示原因，不允许永久空白。

## 实现步骤

- 设计删除 API 请求/响应和失败清单；
- 增加指定快照/会话删除 UI 与确认流程；
- 更新 session/ledger 的一致性策略；
- 为趋势卡显示基线时间、目标时间、盘符和失败原因；
- 统一趋势卡与对比页的字段、总量和 leaf-only 口径；

## 验收

快照页可明确删除指定目标，其他快照保留；删除后刷新页面不再出现目标记录；趋势卡在满足窗口条件时显示变化，不满足时显示“暂无对比基线”及原因；趋势卡点击进入对比页后基线、根和目标一致。

## DoD/回滚

DoD：删除粒度有需求确认、API/UI/安全/台账测试齐全、趋势边界全部通过。回滚：恢复旧快照列表和撤销入口，隔离目录测试产物可清理。

# 六、R3：自动扫描与扫描进度体验

## 阶段信息

- 覆盖问题：5、10。
- 前置：R1；产品负责人确认自动扫描策略。
- 主要定位：`main.js`、`components/scan.js`、`components/storage.js`、`index.html`、`style.css`。

## 设计

在实现前二选一并记录：

- **方案 A：自动模式**：页面 ready 后自动启动一次全量扫描，完成后自动保存；保留手动重试/停止/失败恢复入口；避免刷新页面重复启动；
- **方案 B：当前手动模式**：保留按钮，但优化文案、进度、耗时和保存流程，不删除手动操作。

无论哪种方案，都定义幂等键、扫描启动条件、无 Everything、重复打开、部分完成、保存失败和停止后的行为。ETA 只能在后端提供可可靠估算时展示，否则显示已用时和当前阶段，不伪造预计时间。

## 实现步骤

- 增加启动条件和一次性触发保护；
- 明确自动保存与手动保存的互斥关系；
- 将进度拆成总百分比、已完成盘、当前盘、已用时；
- 评估是否增加盘内条目数、速度和 ETA；
- 调整扫描卡、概览卡、按钮、chips 和引导块的窄屏布局；
- 对状态轮询、页面刷新和路由切换做恢复处理。

## 测试/验收

覆盖冷启动、刷新、Everything 未就绪、单盘、多盘、重复打开、完成、保存失败、中止和再次扫描。1366×768、1920×1080、357×651 等视口截图检查：状态、按钮、进度、耗时不重叠；自动模式最多启动/保存一次；手动模式的每个按钮有反馈。

## DoD/回滚

DoD：自动/手动策略明确且实现一致，进度信息可读，窄屏截图通过，扫描失败仍可恢复。回滚：保留原手动入口和原保存提示，恢复旧启动逻辑。

## 阶段状态

✅ **已完成（2026-09-05，分支 `stage-d`，变更集 1–4 已推送 origin/stage-d）**：

# 七、R4：目录关系与浏览视图体验

## 阶段信息

- 覆盖问题：2、8、12。
- 前置：R0；R1 的 browse source 和状态稳定。
- 主要定位：`workspace.js`、`components/list.js`、`viz/treemap.js`、`style.css`、`index.html`。

## 设计

先定义“关系目录”。若定义为父子层级，应复用 BrowseIndex 的 parent/children；若定义为快照变化关系，应归入 R2；若定义为链接/引用关系，必须先确认 Everything 数据是否能提供关系证据。视图切换必须满足互斥最终态：只有活动视图可见/可绘制，动画期间的短暂叠加要有明确时限。排行与表格必须有结构性差异，舒适/紧凑必须有可测行高、间距或信息密度差异。

## 实现步骤

- 对三视图容器增加专用状态 class，避免仅依赖中文 aria 文案；
- 切换动画结束后销毁/暂停非活动绘制；
- 为排行、表格、矩形图分别写 DOM 和可见性断言；
- 若关系目录确定为父子树，增加关系导航和面包屑入口；
- 定义排行/表格的列差异与 cozy/compact 的尺寸规范；
- 增加长文件名、窄屏和快速连续切换处理。

## 测试/验收

固定数据依次切换 treemap→ranking→table→treemap，在 0/100/500ms 和结束时采样 hidden/class/canvas/动画数量；确认最终只有活动视图绘制。对排行/表格测量行高和列结构；关系目录按定义的父子/引用/变化场景执行。

## DoD/回滚
