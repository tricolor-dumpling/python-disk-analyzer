## 2. 逐项核查记录

### 1. 对比功能一直显示“正在对比，请稍候”

**核查结论：未能仅凭当前静态代码确认仍必现；历史问题需要真实快照回归。** 当前 `web/static/js/app/pages/compare.js` 已有 `postJson("/api/compare")` 的成功、异常、扫描中 409、异机确认分支，成功后调用 `renderReport`，异常后恢复按钮并隐藏 loading（约 201-265、430-467 行）。后端 `app.py` 604-684 行也有完整对比响应。

**必须验证：**准备同一根目录的两份有效快照，进入 `#/compare`，分别验证默认基线、手工选择基线、无快照、扫描中、快照损坏五种情况；记录 Network 中 `/api/compare` 的状态码、响应时间与 UI 状态是否从 loading 收敛。

**后续定位：**`pages/compare.js:201-265`、`app.py:604-684`、`compare.py`。

### 2. 视图切换后底层仍有矩形图

**核查结论：静态代码已有防护，当前未确认复现。** `workspace.js:377-409` 根据 `APP_STATE.view.mode` 切换，`finishViewSwap`（441-449）对旧容器设置 hidden/class；切离矩形图还调用 `treemapView.pause()`。CSS `style.css:122-124` 使用两个绝对定位容器，动画期间短暂同时可见是设计行为。

**风险点：**快速连续切换时 `crossfadeView` 通过 `viewSeq` 丢弃旧动画（411-439），但需要真实逐帧截图确认旧 canvas 是否在动画结束后仍留存；“底层渲染效果删过”可能是动画叠加而不是最终状态错误。

**必须验证：**加载数据后矩形图→排行→表格→矩形图连续点击，分别在 0ms、100ms、500ms 后截图并检查 `#treemap-wrap` 的 `hidden`、`#table-wrap` 的 `hidden/class` 和 canvas 是否仍绘制。

### 3. 管理快照没有删除指定快照

**核查结论：确认存在。** 快照页 `snapshots.js:456-476` 只有“创建快照”和“撤销最近保存”；`app.py` 仅有 `POST /api/save/undo`（525-586）以及 `GET /api/snapshots`，没有按 `session_id`、根或 `snapshot_path` 删除的 API。列表中的“对比此快照”不是删除功能。

**影响：**用户只能删除最近一次保存，无法清理旧的单盘快照或单个会话；一键清空是全量破坏操作，不能替代指定删除。

**后续定位/修改入口：**`app.py:525-586`、`app.py:592-601`、`snapshots.js:124-186`、快照页模板常量 `snapshots.js:456-476`。修改前需先确定删除粒度、路径边界校验、台账回滚和会话清单一致性。

### 4. 较昨日/较上周没有显示

**核查结论：当前已实现，但显示有明确前置条件。** `snapshots.js:203-287` 定义：较昨日为 `0 < Δt ≤ 24h`，较上周为 `24h < Δt ≤ 7d`；`pickTrendForSlot` 找不到窗口内同盘基线就返回空态。两张卡由 `renderTrendCards` 异步调用 `/api/compare`（366-385、341-364）。

**可能造成“没有显示”的原因：**仅有一份快照；两份快照不在对应窗口；多盘但没有同一盘符的合格基线；系统时间/快照 `created_at` 异常；对比请求失败后卡片显示“对比失败”。

**必须验证：**用固定时间夹具分别构造 23h、25h、8d、同一时刻、跨盘快照，核对“较昨日/较上周”的选取与卡片状态；同时确认两张卡的差值口径是否与对比页一致（均调用 `/api/compare`，当前报告为 leaf-only）。

### 5. 页面打开自动全量扫描并自动保存

**核查结论：当前未实现用户要求。** `main.js:228-255` 启动时读取设置、刷新快照/扫描状态/概览并等待健康门控；`topbar.js:81-95` 仅在健康 ready 后自动浏览首根，没有调用 `startFullscan`。`scan.js:137-153` 的全量扫描仍由按钮触发；`maybePromptSave`（339-350）只有 `autoSaveSetting` 为真才自动保存，否则弹提示。

**当前界面仍保留：**顶栏“开始扫描”（`index.html:76-89`）、扫描卡保存按钮（`scan.js:408-410` 接线）、快照页“创建快照”（`snapshots.js:464-466`）。

**注意：**这属于产品流程变更，不应直接删除按钮而不先定义扫描失败、用户停止、无 Everything、磁盘占用与自动保存失败时的恢复入口。

**测试建议：**在扫描进行中分别观察首次进入、切换排行/表格、切换盘符、停止扫描、`prefers-reduced-motion` 五种状态；录屏标注异常发生的时间点，保存对应 DOM/CSS 状态，避免只凭静态截图修改。

### 7. 第二次全量扫描迟迟没有结果

**核查结论：存在需要重点排查的状态/锁链路，但未执行真实第二次扫描。** 后端 `fullscan.py` 通过全局扫描锁串行化；`app.py:366-376` 对重复启动返回 409；前端 `scan.js:155-195` 使用单轮询定时器，理论上避免重复 poll。停止则由 `request_stop_scan` 置位事件后继续轮询（69-81）。

**重点观察：**第一次完成后 `scan_version`、`saved_scan_version`、`BROWSE_INDEX`、`result` 是否清理/替换；第二次启动是否真的返回 `started=true`；后台线程是否被旧的 `cancel_event` 或 SDK 锁阻塞；状态接口是否一直返回 `running=true`。

**必须测试：**完成→立即第二次启动；完成→保存→第二次启动；第一次中途停止→第二次启动；第二次启动时连续点击；每秒采集 `/api/fullscan/status` 直到终态，并保留服务端日志和线程状态。

### 8. 没有关系目录功能

**核查结论：确认缺失。** 当前能力是目录浏览、排行、表格、矩形图、对比和快照。未发现“关系目录”命名、关系图数据结构、关系 API 或对应 UI。`workspace.js` 的 treemap 是空间占比图，不是目录关系图。

**后续需先定规格：**关系是父子树、目录引用/链接关系、快照间变化关系，还是目录依赖关系。否则无法直接定位为一个单一实现缺陷。

### 9. 停止扫描没有反馈

**核查结论：当前版本已有反馈实现，但停止不是同步硬中断。** `scan.js:69-81` 发停止请求后将状态设为“正在停止…”，并继续轮询；`scan.js:282-289、321-329` 在完成边沿显示“已停止，已完成部分可浏览”；后端 `app.py:388-391` 返回 `stopped` 与状态。

**仍需验证：**SDK 调用是否可被协作取消；停止请求到 `running=false` 的耗时；停止期间按钮是否重复可点；停止失败/网络断开是否有反馈。若用户说“没有反馈”，很可能是前端只在请求返回或下一次轮询后更新，而不是没有状态设计。

### 10. 扫描区域拥挤、进度不友好

**核查结论：部分已缓解，仍存在需求缺口。** 当前状态文案 `scan.js:298-304` 为“正在扫描 x/y：当前盘”，前端还显示百分比与已用时 `scan.js:270-280`；概览也显示“扫描中 百分比 · 已完成 x/y 个盘”（`storage.js:233-236、266-268`）。但没有预计完成时间，也没有盘内条目/字节进度；扫描卡、停止按钮、保存提示、盘符 chips 叠加时是否拥挤仍需 UI 实测。

**必须验证：**窄屏、中文长盘名、双盘/多盘、扫描中切换页面四种布局截图；记录进度是否长时间停在盘间平台期。

### 11. 主题扩散动画底部接触时瞬间铺满

**核查结论：需浏览器视觉复现，代码存在明确边界条件。** `theme.js:79-99` 使用点击坐标计算到四角最大半径，并对 `::view-transition-new(root)` 设置 clip-path 圆形动画。设置页主题变更在 `settings.js:174-187` 用单选项容器中心点模拟坐标。

**风险点：**View Transition 伪元素、不同浏览器对 `document.documentElement.animate` 的支持、伪元素裁剪与根背景绘制时序，都可能导致扩散末端瞬间切换；设置单选的中心点不是鼠标真实坐标，而是控件矩形中心。

**测试矩阵：**顶栏按钮四角/边缘点击、设置三态单选四角点击、系统主题跟随、Edge 与 reduced-motion，逐项录屏。

### 12. 排行/表格与舒适/紧凑差异小

**核查结论：功能实现存在，体验差异需视觉验收。** `workspace.js:377-409` 负责三视图切换；`list.js:390-459` 根据 `APP_STATE.view.mode` 生成排行或表格；密度切换在 `workspace.js:742-749`，CSS 行高主要在 `style.css` 的列表规则中。

**测试方法：**同一数据下对比 DOM 结构、列信息、操作按钮、排序/筛选行为和实际 `getBoundingClientRect().height`；分别截图排行、表格、cozy、compact。若只是字号/行高差，需记录设计期望而非直接判定功能错误。

### 13. 第二次扫描停止后仍显示“来自内存缓存”，扫描冲突

**核查结论：缓存徽章误标已确认，停止冲突需流程复现。** `workspace.js:609-620` 的逻辑是：只要 `data.scanning` 不为真就显示 `browse-cache-badge`。后端普通 SDK 浏览响应 `app.py:294-319` 没有 `scanning` 字段，因此一次真实 SDK 扫描成功也会被标成“来自内存缓存”。这直接造成用户看到的缓存提示不可信。

**停止后冲突验证：**停止时检查 `fullscan.status()` 的 `stop_requested/stop_reason/running/result_ready`，再浏览已完成盘和未完成盘；确认是否仍复用停止前 `APP_STATE.lastBrowseData`、`BROWSE_INDEX` 与 fullscan result。

**后续定位：**`workspace.js:609-620`、`app.py:227-319`、`fullscan.py` 状态生命周期。

### 14. CSV/JSON 到处不可用

**核查结论：当前代码已提供导出实现，因此原问题在当前版本可能已修复或只剩特定场景。** 后端 `/api/export` 位于 `app.py:756-813`；前端全量导出接线在 `scan.js:412-418`，命令面板也在 `main.js:170-171` 提供 CSV/JSON；列表还有前端“导出所选 CSV”（`list.js:142-184`）。

**仍需回归：**无全量结果应返回 404 JSON；全量完成后分别点击主入口、命令面板、选中条目导出；校验 `Content-Disposition`、BOM、JSON UTF-8、根参数、空结果和中止结果。原始错误中的“暂无可导出的全量扫描结果”在无结果场景仍是预期保护，不等同于导出功能必然不可用。

### 15. 设置排版与主题扩散中心

**核查结论：分两部分。** 设置弹窗的主题选项、自动保存、数据目录、Everything 状态、危险操作均有固定布局（`index.html:156-216`）；是否“对不齐”属于视觉验收项，静态代码无法量化。主题扩散在 `theme.js:79-99` 使用事件坐标，顶栏真实点击理论上取点击点；但设置单选在 `settings.js:176-187` 传入的是选项矩形中心，不是鼠标事件坐标，因此用户从选项不同位置点击时扩散中心不会跟随真实点击点。

**需实测：**设置弹窗截图检查按钮基线、左右间距、窄屏换行；顶栏与设置选项分别点击中心/边缘并录屏。

### 16. `/api/fullscan/status` 日志很多是否正常

**核查结论：正常但有噪声。** `scan.js:169-195` 每次轮询 GET `/api/fullscan/status`，扫描中通过 `schedulePollFullscan` 约每秒继续；`main.js:240` 页面启动也会立即调用一次。Flask 开发服务器会为每个请求打印 access log，200 表示成功，不是异常。若希望 Web 输出更干净，应配置日志过滤/生产 WSGI 日志策略，但这不影响接口。

### 17. 点击 Everything 后一直显示扫描中

**核查结论：当前文案与状态来源需区分。** 健康检查在扫描锁被占时返回 `busy:true`（`app.py:108-115`），前端显示“扫描中…”（`topbar.js:30-37`）；真正全量扫描状态来自 `/api/fullscan/status`。如果 `busy` 长期存在，应采样该接口并同时检查 `fullscan.status().running`、线程、`SCAN_LOCK` 和 SDK 调用是否返回。单凭“点击 Everything”不能证明一定是前端显示 bug。

**复现记录模板：**时间、点击动作、health JSON、fullscan status JSON、浏览器 Network 请求、服务端线程/日志；至少连续采样 30 秒。

### 18. 主题和使用指引中间按钮无反应

**核查结论：当前模板该按钮是顶栏“开始扫描”，不是无功能占位。** `index.html:70-95` 的顺序为主题→开始扫描→使用指引；`main.js:63-93` 绑定 `btn-scan-top`，空闲时导航到工作台并启动扫描，扫描中点击则回工作台。若点击无反应，应检查按钮是否处于扫描中、`start()` 是否因模块加载异常提前失败、或页面使用的是旧构建/旧实例。

### 20. 资源缓存问题

**核查结论：已确认应用层缓存提示口径问题，未发现普通 HTTP 缓存证据。** `workspace.js:609-620` 只以 `data.scanning` 是否存在判断缓存；而正常 SDK 浏览响应 `app.py:294-319` 不提供该字段，所以真实 SDK 结果也会显示“来自内存缓存”。此外工作区还保留 `browsesCache`（`workspace.js:244-253`，LRU 16）和 `APP_STATE.lastBrowseData`，它们是应用内数据缓存，不是浏览器静态资源缓存。

**需分别排查：**响应 headers/DevTools Disable cache 验证 HTTP 缓存；再对比同一路径的 index 命中、SDK 直扫、全量扫描中三类响应，记录 `source`、时间戳与 UI 徽章是否一致。

### 21. Web 启动输出 CLI 日志

**核查结论：普通控制台运行仍会输出，打包窗口模式仅部分隐藏。** `app.py:853-867` 只对 `stdout/stderr is None` 的 windowed 场景重定向；`run_server:907-937` 仍启用 Flask 开发服务器，且启动/Everything 检查及 access log 会输出。`utils.log` 的 quiet 机制主要服务 CLI，不等价于 Web 日志关闭。

**注意：**开发环境保留 access log 有利于排查；发布环境应使用日志级别过滤、专用 WSGI server 或将 startup/access log 路由到文件，不应静默真正错误。
